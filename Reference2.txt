# NoiseSense — Online Deployment Plan

For your capstone, I recommend a hosted frontend, hosted backend, and managed PostgreSQL database, with one public URL that you can open on your phone or laptop.

This setup lets you demonstrate the complete NoiseSense workflow without depending on your laptop as a server during your presentation.

## 1. Recommended deployment architecture

Student phones and laptops

Open the NoiseSense public URL

Frontend hosting — Vercel

React · TypeScript · Tailwind CSS · PWA

Serves the user interface over HTTPS

Backend hosting — Render

Node.js · Express · Socket.IO

Validates readings, aggregates data and broadcasts updates

Managed database — Neon

PostgreSQL + PostGIS, subject to plan support

Stores readings, timestamps and aggregated data

The architecture is deliberately separated into three deployable services. If the UI needs changes, you can update the frontend without redesigning the database or rewriting the measurement logic.

One important deployment detail: the backend must remain reachable for live updates. Some hosting plans suspend inactive services or impose usage limits, so we should verify the selected plan's current behaviour before committing to it.

## 3. Public URL structure

Once deployed, your application will have URLs similar to these examples; the actual addresses will be assigned by the hosting providers.

| Component    | Example format                                       |
| ------------ | ---------------------------------------------------- |
| Frontend     | `https://noisesense-example.vercel.app`              |
| Backend API  | `https://noisesense-api-example.onrender.com`        |
| Health check | `https://noisesense-api-example.onrender.com/health` |

Your presentation needs only the frontend URL. The browser will communicate with the backend behind the scenes.

For microphone and location access, the deployed frontend must use HTTPS and request the user's permission. These browser APIs are restricted to secure contexts.&#x20;

## 5. Environment configuration

The frontend and backend need a small set of configuration variables.

Frontend — `.env.local`

```
VITE_API_URL=http://localhost:5000
```

Use the local URL during development. Replace it with the deployed backend URL for production.

Backend — `.env`

```
PORT=5000
DATABASE_URL=your_database_connection_string
FRONTEND_URL=http://localhost:5173
```

The database connection string and any credentials must remain on the backend. Never commit `.env` files or expose database passwords in frontend code.

For production, the backend must allow the actual frontend origin through CORS, use the platform-provided port, and configure Socket.IO for the deployed frontend URL. The client should reconnect after network interruptions and fetch the latest map state when it reconnects.

## 6. Deployment and testing sequence

I recommend this order so that we do not attempt to deploy an incomplete application.

1. Develop locally: Create the frontend, backend and database schema. Verify that a reading can be submitted and retrieved.
2. Test on a phone: Access the development environment through an appropriate secure setup and verify microphone and GPS permissions.
3. Deploy the database: Create the managed PostgreSQL instance, enable PostGIS, and apply the schema.
4. Deploy the backend: Configure database credentials, CORS, health checks and Socket.IO. Test the public API.
5. Deploy the frontend: Connect the repository to Vercel and set the production API URL.
6. Run an end-to-end test: Open NoiseSense on two phones, submit a measurement from one and confirm that the other receives the updated map.
7. Prepare for the presentation: Test the public URL, verify database persistence, check hosting sleep behaviour and preload sample data for the map.

## 7. Final recommendations

- Use Vercel + Render + Supabase as the initial hosting combination.
- Start with anonymous readings and no login system.
- Keep the backend responsible for validation and aggregation.
- Store only the sound-level measurements and necessary location metadata; do not upload or retain raw audio.
- Seed the database with clearly labelled demonstration data, while distinguishing it from live readings.
- Verify microphone and GPS behaviour on the actual phones you will use for the demonstration.

The most important success criterion is that NoiseSense must work as one connected system, not just as a good-looking frontend.

Next step: Establish the project structure and development configuration, then implement the dashboard and sensing-to-backend workflow in stages. We should not begin with hosting configuration alone; a working local application will make deployment much more predictable.
