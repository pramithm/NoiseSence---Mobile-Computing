# NoiseSense — Architecture and Feasibility Plan

Based on your decisions, I recommend building NoiseSense as a mobile-first Progressive Web App (PWA) with a central backend, an interactive noise map, and real-time synchronization.

The objective is to deliver three things successfully: a professional user interface, a working end-to-end application, and a clear demonstration of Mobile Computing concepts.

## 1. Finalized project definition

Platform\
Mobile-first PWA that works in a mobile browser and can be installed on supported devices.

Connectivity\
Internet-based client-server communication using a hosted backend.

Core demonstration\
One phone submits a noise reading, the backend processes it, and another phone's map updates automatically.

Quality target\
A polished dashboard, intuitive measurement flow, interactive map, useful statistics and reliable error handling.

This preserves the central design in your NoiseSense presentation: microphone sensing, GPS tagging, backend aggregation, and a shared real-time heat map.&#x20;

## 3. Proposed system architecture

The system will have four main layers: mobile client, sensing services, backend services and data storage.

### Layer 1 — Mobile PWA

React · TypeScript · Tailwind CSS

Dashboard · Measure · Map · History

HTTPS REST API + WebSocket

### Layer 2 — Backend

Node.js · Express · Socket.IO

Validation · Aggregation · Rate limiting · Broadcasting

### Layer 3 — Database

PostgreSQL + PostGIS

Readings · Geographic cells · Timestamps · Aggregates

### Layer 4 — Shared visualization

Leaflet map with live noise updates

Connected phones receive the latest map data.

The fourth layer represents the output of the system, not an additional backend service.

### How a reading travels through the application

1. Capture: A user taps Measure and grants microphone permission. The application samples audio for approximately 10 seconds.
2. Locate: The application obtains the phone's location and reported GPS accuracy.
3. Submit: A measurement containing the estimated noise level, coordinates and timestamp is sent to the backend.
4. Validate and aggregate: The backend checks the input and calculates a representative level for the corresponding geographic grid cell.
5. Store: The reading is saved in PostgreSQL.
6. Broadcast: Socket.IO sends updated cell information to connected map clients.
7. Display: Other users see the updated heat map without refreshing their browsers.

A practical detail: the database should store individual readings separately from aggregated map-cell statistics. This makes history, filtering and recalculation easier.

## 5. Feasibility assessment

The project is feasible at moderate complexity if we keep the first version focused.

| Feature                    | Feasibility          | Main consideration                            |
| -------------------------- | -------------------- | --------------------------------------------- |
| Responsive PWA             | High                 | Browser compatibility and HTTPS               |
| Microphone measurement     | High for an estimate | Device-dependent calibration                  |
| GPS tagging                | High                 | User permission and signal quality            |
| Persistent database        | High                 | Hosted database configuration                 |
| Live map updates           | High                 | WebSocket connection management               |
| Noise heat map             | High                 | Enough valid readings per area                |
| Offline measurement queue  | Moderate             | Storage and retry handling                    |
| Accurate, calibrated dB(A) | More difficult       | Reference measurements and device differences |

The primary technical risk is not building the UI or connecting the database. It is producing meaningful sound-level estimates across different phone models.

We should clearly label the measurement as an estimated sound level until calibration has been validated. We also should not label a reading harmful solely because it crosses a threshold without accounting for measurement uncertainty and exposure duration.

### What we should not build initially

To keep the project achievable, defer:

- Machine-learning classification of traffic, construction and music.
- Complex user accounts and social features.
- Native Android and iOS applications.
- Advanced city-authority reporting.
- Predictive noise modelling.
- Elaborate offline synchronization across devices.

These can be future enhancements rather than requirements for the initial submission.

## 6. Backend API plan

The first version can be implemented with a small set of endpoints.

| Endpoint                          | Purpose                                  |
| --------------------------------- | ---------------------------------------- |
| `POST /api/readings`              | Validate and save a new reading          |
| `GET /api/readings`               | Retrieve recent readings and history     |
| `GET /api/heatmap`                | Retrieve aggregated geographic cell data |
| `GET /api/stats`                  | Retrieve dashboard statistics            |
| Socket.IO event: `heatmap:update` | Notify clients about updated map cells   |

The API should validate coordinate ranges, timestamps and plausible sound-level values. It should also apply submission limits and avoid trusting a client-provided device identifier as proof of authenticity.

We can start with anonymous submissions and no login system. This reduces implementation time and personal-data collection.

## 8. What a successful final demonstration should prove

Your capstone should demonstrate the entire workflow rather than just showing static screens.

A phone captures a measurement and attaches its location.

The backend stores and aggregates the reading.

A second phone receives the updated map automatically.

The user can view reading history and area statistics.

The app handles denied permissions, weak location fixes and failed network requests gracefully.

For a reliable classroom demonstration, we should also seed the database with clearly labelled sample readings from several areas. That allows the map to look populated even before multiple participants contribute real measurements.

My recommendation: Use React, TypeScript, Tailwind CSS, Node.js, Express, PostgreSQL/PostGIS, Leaflet and Socket.IO. Implement the complete sensing-to-live-map workflow first, then polish the UI and add history and statistics.
